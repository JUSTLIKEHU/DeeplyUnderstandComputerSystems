### 如何将win上的ssh连接转发到Wsl上

要将 Windows 上的 SSH 连接转发到 WSL 2，您可以使用 Windows 的端口转发功能。以下是一般步骤：

1. 确保 WSL 2 中已经安装和配置了 SSH 服务器。可以使用 OpenSSH 服务器作为 SSH 服务器。

2. 在 WSL 2 终端中获取 WSL 2 的 IP 地址。运行以下命令：
   
   ```bash
   ip addr | grep eth0
   ```
   
   或者：
   
   ```bash
   hostname -I
   ```
   
   记下 WSL 2 的 IP 地址，稍后将用到。

3. 在 Windows 上打开 PowerShell 或命令提示符。

4. 使用以下命令启用端口转发（将 Windows 上的某个端口转发到 WSL 2 的 SSH 服务器）：
   
   ```bash
   netsh interface portproxy add v4tov4 listenaddress=windows-ip listenport=windows-port connectaddress=wsl2-ip connectport=wsl2-port
   ```
   
   其中：
   
   - `windows-ip` 是 Windows 主机的 IP 地址。
   - `windows-port` 是要转发的 Windows 端口（例如，22 是 SSH 默认端口）。
   - `wsl2-ip` 是 WSL 2 的 IP 地址。
   - `wsl2-port` 是 WSL 2 中 SSH 服务器监听的端口（例如，22 是 SSH 默认端口）。
   
   请替换命令中的相应值。运行此命令后，端口转发将被设置。

5. 现在，您可以使用 SSH 客户端连接到 Windows 主机的转发端口。在其他设备上的 SSH 客户端中，连接到 Windows 主机的 IP 地址和转发的端口。例如：
   
   ```bash
   ssh username@windows-ip -p windows-port
   ```
   
   其中：
   
   - `username` 是 WSL 2 中的用户名。
   - `windows-ip` 是 Windows 主机的 IP 地址。
   - `windows-port` 是转发的端口。
   
   输入此命令后，系统将提示您输入 WSL 2 用户的密码。输入正确的密码后，您将成功连接到 WSL 2 中的 SSH 服务器，并可以在远程终端中执行命令。

请注意，以上步骤涉及到网络配置和端口转发，确保您具备适当的权限并理解相关网络安全风险。

### wsl文件系统

首先要了解 WSL 中的[两种文件系统](https://p3terx.com/go/aHR0cHM6Ly9ibG9ncy5tc2RuLm1pY3Jvc29mdC5jb20vd3NsLzIwMTYvMDYvMTUvd3NsLWZpbGUtc3lzdGVtLXN1cHBvcnQv)：

- **VolFs**
  
  着力于在 Win­dows 文件系统上提供完整的 Linux 文件系统特性，通过各种手段实现了对 In­odes、Di­rec­tory en­tries、File ob­jects、File de­scrip­tors、Spe­cial file types 的支持。比如为了支持 Win­dows 上没有的 In­odes，VolFs 会把文件权限等信息保存在文件的 NTFS Ex­tended At­trib­utes 中。
  
  WSL 中的 `/` 使用的就是 VolFs 文件系统。

- **DrvFs**
  
  着力于提供与 Win­dows 文件系统的互操作性。与 VolFs 不同，为了提供最大的互操作性，DrvFs 不会在文件的 NTFS Ex­tended At­trib­utes 中储存附加信息，而是从 Win­dows 的文件权限（Ac­cess Con­trol Lists，就是你右键文件 > 属性 > 安全选项卡中的那些权限配置）推断出该文件对应的的 Linux 文件权限。
  
  所有 Win­dows 盘符挂载至 WSL 下的 `/mnt` 时都是使用的 DrvFs 文件系统。

简单来说就是 WSL 对 `/` 目录下的文件拥有完整的控制权，而 `/mnt` 目录中的文件无法被 WSL 完全控制（可修改数据，无法真实的修改权限）。WSL 对 `/mnt` 目录中权限的修改不会直接记录到文件本身，而在 Win­dows 下对文件权限的修改直接可作用到 WSL 。关于权限在微软开发者博客中有[更详细的说明](https://p3terx.com/go/aHR0cHM6Ly9kZXZibG9ncy5taWNyb3NvZnQuY29tL2NvbW1hbmRsaW5lL2NobW9kLWNob3duLXdzbC1pbXByb3ZlbWVudHMv)。

### Systemd

Systemd 是一个系统和服务管理器，用于在 Linux 操作系统中启动和管理系统服务。它引入了一种新的启动系统服务的方法，取代了传统的 SysV init 和 Upstart 系统。Systemd 使用单元文件（Unit Files）来配置服务，这些文件描述了服务的启动和管理方式。

#### Systemd 配置文件的结构

一个典型的 systemd 单元文件包含以下几部分：

1. **[Unit] 部分**：描述服务的基本信息，包括描述、依赖关系等。

   ```ini
   [Unit]
   Description=描述服务的作用
   After=network.target  # 指定服务应该在网络服务启动后启动
   ```

2. **[Service] 部分**：定义服务的具体行为，包括启动、停止和重启的命令等。

   ```ini
   [Service]
   ExecStart=/path/to/your/executable  # 指定启动服务的命令
   ExecStop=/path/to/stop/command      # 指定停止服务的命令（可选）
   Restart=on-failure                  # 在服务失败时自动重启
   ```

3. **[Install] 部分**：定义服务安装相关的信息，包括服务启用的目标（target）。

   ```ini
   [Install]
   WantedBy=multi-user.target  # 指定服务在多用户模式下启动
   ```

`WantedBy` 是 systemd 单元文件 `[Install]` 部分的一个选项，用于定义单元安装后将被哪些目标（targets）所需要（wanted）。这些目标决定了服务或单元在什么情况下会被启动。常见的目标类型有许多，下面列出了一些常见的和常用的目标类型及其用途：

**常见的 `WantedBy` 类型**

1. **multi-user.target**：

   - 表示多用户模式（类似于传统的运行级别 3）。在这种模式下，系统启动到命令行环境，网络服务和多用户支持都会启动，但不包括图形用户界面 (GUI)。
   - 常用于服务器和不需要图形界面的系统。

   ```ini
   WantedBy=multi-user.target
   ```

2. **graphical.target**：

   - 表示图形用户界面模式（类似于传统的运行级别 5）。在这种模式下，系统启动到图形界面，包括所有的 multi-user.target 服务。
   - 常用于桌面系统或需要图形界面的服务器。

   ```ini
   WantedBy=graphical.target
   ```

3. **basic.target**：

   - 表示基本系统模式，包括挂载文件系统、启动基本设备和启动日志系统等。
   - 是 `multi-user.target` 和 `graphical.target` 的基础。

   ```ini
   WantedBy=basic.target
   ```

4. **default.target**：

   - 表示系统启动时的默认目标。通常是一个符号链接，指向 `multi-user.target` 或 `graphical.target`，具体取决于系统配置。

   ```ini
   WantedBy=default.target
   ```

5. **network.target**：

   - 表示网络已启动，但不一定配置完毕。适用于需要在网络服务启动后立即运行的服务。

   ```ini
   WantedBy=network.target
   ```

6. **sysinit.target**：

   - 表示系统初始化，包括挂载文件系统、启动 udev 和其它基础设施服务。
   - 在所有其他目标之前启动。

   ```ini
   WantedBy=sysinit.target
   ```

7. **remote-fs.target**：

   - 表示所有远程文件系统已挂载。适用于依赖远程文件系统的服务。

   ```ini
   WantedBy=remote-fs.target
   ```

8. **shutdown.target**：

   - 表示系统正在关闭。可以在系统关机时运行特定的服务或脚本。

   ```ini
   WantedBy=shutdown.target
   ```

#### 创建和配置 systemd 服务

以下是创建和配置一个自启动 systemd 服务的步骤：

1. **创建服务单元文件**： 假设我们要创建一个名为 `my_service` 的服务，首先需要在 `/etc/systemd/system/` 目录下创建一个单元文件，文件名为 `my_service.service`。

   ```shell
   sudo nano /etc/systemd/system/my_service.service
   ```

2. **编辑单元文件**： 在文件中添加以下内容，根据需要进行修改：

   ```ini
   [Unit]
   Description=My Custom Service
   After=network.target
   
   [Service]
   ExecStart=/usr/bin/my_executable  # 替换为实际的可执行文件路径
   Restart=on-failure
   
   [Install]
   WantedBy=multi-user.target
   ```

3. **保存并关闭文件**。

4. **重新加载 systemd 配置**：

   ```sh
   sudo systemctl daemon-reload
   ```

5. **启用并启动服务**： 启用服务使其在系统启动时自动启动。

   ```sh
   sudo systemctl enable my_service
   sudo systemctl start my_service
   ```

6. **检查服务状态**： 查看服务的状态以确保其正确启动。

   ```sh
   sudo systemctl status my_service
   ```

#### 示例

假设我们有一个脚本 `/usr/local/bin/my_script.sh`，我们希望将其配置为一个 systemd 服务并在系统启动时自动运行。

1. 创建单元文件：

   ```sh
   sudo nano /etc/systemd/system/my_script.service
   ```

2. 编辑单元文件：

   ```ini
   [Unit]
   Description=My Script Service
   After=network.target
   
   [Service]
   ExecStart=/usr/local/bin/my_script.sh
   Restart=on-failure
   
   [Install]
   WantedBy=multi-user.target
   ```

3. 保存文件并重新加载 systemd 配置：

   ```sh
   sudo systemctl daemon-reload
   ```

4. 启用并启动服务：

   ```sh
   sudo systemctl enable my_script
   sudo systemctl start my_script
   ```

5. 检查服务状态：

   ```sh
   sudo systemctl status my_script
   ```

通过这些步骤，你可以创建和配置一个 systemd 服务，使其在系统启动时自动运行。

#### QA:

##### 如果没有配置ExecStop，systemctl stop 命令是否生效？为什么？

**A:** (answered by chatgpt-4o)

如果没有在 systemd 单元文件中配置 `ExecStop` 指令，`systemctl stop` 命令仍然会生效，但它的工作方式会依赖于 systemd 的默认行为。

###### 默认行为

当 `ExecStop` 没有被显式配置时，systemd 会默认发送一个 `SIGTERM` 信号给服务的主进程，以请求其停止。这是因为大多数守护进程会在接收到 `SIGTERM` 信号后，进行清理并优雅地退出。

###### 工作原理

1. **启动服务**：当你使用 `systemctl start my_service` 启动服务时，systemd 会执行 `ExecStart` 中定义的命令，并跟踪由此命令生成的主进程。
2. **停止服务**：当你使用 `systemctl stop my_service` 停止服务时，systemd 会向主进程发送一个 `SIGTERM` 信号。大多数情况下，这会使服务优雅地关闭。

###### 具体示例

假设我们有一个简单的 systemd 单元文件，没有配置 `ExecStop`：

```ini
[Unit]
Description=My Custom Service
After=network.target

[Service]
ExecStart=/usr/bin/my_executable
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

1. **启动服务**：

   ```sh
   sudo systemctl start my_service
   ```

2. **停止服务**：

   ```sh
   sudo systemctl stop my_service
   ```

###### 为什么 systemctl stop 仍然生效？

`systemctl stop` 生效的原因是 systemd 在没有 `ExecStop` 的情况下，会采取默认的行为，即发送 `SIGTERM` 信号给服务的主进程。这个信号通常会被守护进程捕获并用于触发优雅关闭过程。以下是这个过程的详细解释：

1. **SIGTERM 信号**：`SIGTERM` 是一个标准的 Unix 信号，用于请求进程终止。大多数守护进程会捕获这个信号，执行必要的清理工作（如保存状态、释放资源等），然后退出。
2. **systemd 的信号处理**：systemd 管理的每个服务都有一个主进程 ID (PID)，它会向该主进程发送 `SIGTERM` 信号。systemd 假设守护进程能够正确处理这个信号并优雅地终止。

###### 自定义停止命令

如果服务需要执行特殊的停止命令或需要特定的清理步骤，可以在单元文件中显式配置 `ExecStop`。例如：

```ini
[Unit]
Description=My Custom Service
After=network.target

[Service]
ExecStart=/usr/bin/my_executable
ExecStop=/usr/bin/my_stop_script.sh  # 自定义停止命令
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

配置了 `ExecStop` 后，systemd 会在停止服务时执行该命令，而不是发送 `SIGTERM` 信号。

###### 总结

没有配置 `ExecStop` 时，`systemctl stop` 命令仍然生效，因为 systemd 会默认发送 `SIGTERM` 信号给服务的主进程。这个信号通常足以使大多数守护进程优雅地关闭。如果服务需要特定的停止行为，可以通过配置 `ExecStop` 来实现。

## GDB

### .gdbinit

`.gdbinit` 文件，这是一个针对 GDB（GNU Debugger）的配置文件。

**`.gdbinit` 文件是在启动 GDB 调试器时自动加载的，它可以包含一系列 GDB 命令，用于自定义 GDB 的行为、定义别名、设置断点等**。这样可以简化调试过程，并根据你的需要进行个性化定制。

`.gdbinit` 文件可以位于用户的家目录（例如 `/home/user/.gdbinit`）或者工作目录下。在调试会话开始时，GDB 会自动加载该文件并执行其中的命令。

一些常见的用途包括：

1. 定义别名：通过定义别名来简化常用的 GDB 命令，例如将 `p` 定义为 `print`。
2. 设置断点：在 `.gdbinit` 中设置常用的断点，以便在每次启动调试会话时自动设置。
3. 配置显示选项：修改 GDB 的显示选项，例如禁用特定的警告、启用或禁用自动打印变量等。

在编写 `.gdbinit` 文件时，需要小心避免引入不必要的影响或潜在的错误。确保只包含你真正需要的配置，以免导致调试过程变得混乱或效率低下。

### set sysroot 与 set solib-search-path的区别

`set sysroot` 和 `set solib-search-path` 都是 GDB 中用于设置调试环境的命令，但它们的作用不同：

1. **`set sysroot`**：
   
   - `set sysroot` 命令用于设置程序运行时的虚拟根目录，它会影响 GDB 对程序的搜索路径和符号文件的加载路径。
   - 当你使用交叉编译环境调试目标程序时，通常会用到 `set sysroot` 命令。你可以将交叉编译环境中的头文件、库文件以及符号文件的路径都设置为相对于 `sysroot` 的路径，这样 GDB 就能正确加载和解析它们。

2. **`set solib-search-path`**：
   
   - `set solib-search-path` 命令用于设置 GDB 在调试过程中搜索共享库（动态链接库）的路径。
   - 当目标程序依赖于某些共享库时，GDB 需要知道在哪里搜索这些共享库，以便正确加载和解析符号。使用 `set solib-search-path` 可以告诉 GDB 在哪里查找这些共享库。

简而言之，`set sysroot` 是为了设置程序运行时的虚拟根目录，而 `set solib-search-path` 是为了设置 GDB 在调试过程中搜索共享库的路径。这两个命令可以一起使用，以确保 GDB 能够正确加载和解析目标程序及其依赖的共享库。

### 免密登录配置

**Linux:**

  要实现VS Code远程免密登录开发机，你需要使用SSH密钥对进行身份验证。以下是设置步骤：

1. 在你的本地机器上生成一个SSH密钥对。如果你已经有一个，你可以跳过这一步。在终端中运行以下命令：

```bash
ssh-keygen -t rsa -b 4096
```

这将在你的`~/.ssh`目录下生成两个文件：`id_rsa`（私钥）和`id_rsa.pub`（公钥）。

2. 将你的公钥复制到远程开发机的`~/.ssh/authorized_keys`文件中。你可以使用`ssh-copy-id`命令来做这个：

```bash
ssh-copy-id -i ~/.ssh/id_rsa.pub your_username@your_remote_host
```

3. 在VS Code中安装"Remote - SSH"扩展。

4. 打开VS Code的SSH配置文件（通常是`~/.ssh/config`），添加一个新的主机配置：

```bash
Host your_remote_host
  User your_username
  HostName your_remote_host_ip
  IdentityFile ~/.ssh/id_rsa
```

5. 在VS Code中，点击左侧边栏的"Remote Explorer"图标，然后选择"SSH Targets"。你应该能看到你刚刚在SSH配置文件中添加的主机。

6. 点击你的主机名，VS Code将会通过SSH连接到你的远程开发机，并在那里启动一个新的VS Code服务器实例。

完成以上步骤后，你应该可以在VS Code中免密登录你的远程开发机了。

**windows:**

在Windows环境下，VS Code远程免密登录开发机的步骤与Linux类似，但是生成和复制SSH密钥的方法有所不同。以下是具体步骤：

1. 在你的Windows机器上生成一个SSH密钥对。你可以使用Git Bash来运行这个命令：

```bash
ssh-keygen -t rsa -b 4096
```

这将在你的`~/.ssh`目录下生成两个文件：`id_rsa`（私钥）和`id_rsa.pub`（公钥）。

2. 将你的公钥复制到远程开发机的`~/.ssh/authorized_keys`文件中。你可以使用`scp`命令来做这个：

```bash
scp ~/.ssh/id_rsa.pub your_username@your_remote_host:~/
```

然后在远程开发机上运行以下命令：

```bash
cat ~/id_rsa.pub >> ~/.ssh/authorized_keys
```

3. 在VS Code中安装"Remote - SSH"扩展。

4. 打开VS Code的SSH配置文件（通常是`C:\Users\YourUserName\.ssh\config`），添加一个新的主机配置：

```bash
Host your_remote_host
  User your_username
  HostName your_remote_host_ip
  IdentityFile C:\Users\YourUserName\.ssh\id_rsa
```

5. 在VS Code中，点击左侧边栏的"Remote Explorer"图标，然后选择"SSH Targets"。你应该能看到你刚刚在SSH配置文件中添加的主机。

6. 点击你的主机名，VS Code将会通过SSH连接到你的远程开发机，并在那里启动一个新的VS Code服务器实例。

完成以上步骤后，你应该可以在VS Code中免密登录你的远程开发机了。

[Service]
Environment="HTTP_PROXY=http://proxy.example.com:8080/"
Environment="HTTPS_PROXY=http://proxy.example.com:8080/"
Environment="NO_PROXY=localhost,127.0.0.1,.example.com"

### 常见命令

1. 使用dockerfile文件来构建镜像

   ```
   docker build -t <镜像名>:<标签> <Dockerfile 所在目录>
   ```

2. 将指定容器保存为镜像

   使用 `docker commit` 命令将容器保存为镜像。语法如下：

   ```bash
   docker commit [OPTIONS] CONTAINER [REPOSITORY[:TAG]]
   ```

   - `CONTAINER` 是容器的 ID 或名称。
   - `REPOSITORY` 是新镜像的仓库名称。
   - `TAG` 是新镜像的标签（版本）。如果不指定 TAG，则默认为 `latest`。

   例如，保存 ID 为 `abcd1234` 的容器为名为 `my-image` 的镜像：

   ```bash
   docker commit abcd1234 my-image
   ```

   这将创建一个名为 `my-image` 的新镜像，基于容器 `abcd1234` 的当前状态。

3. 到处镜像到本地文件

   使用 `docker save` 命令将镜像导出到本地文件。语法如下：

   ```bash
   docker save -o OUTPUT_FILE IMAGE_NAME[:TAG]
   ```

   - `-o OUTPUT_FILE` 指定导出的输出文件路径和名称。
   - `IMAGE_NAME[:TAG]` 是要导出的镜像的名称和标签。

   例如，导出 `my-image` 镜像到当前目录下的 `my-image.tar` 文件：

   ```bash
   docker save -o my-image.tar my-image
   ```

4. 加载本地镜像文件

   ```bash
   docker load -i my-image.tar
   ```

## CMAKE

### INTERFACE|PUBLIC|PRIVATE用法

在 CMake 中，`INTERFACE`, `PUBLIC`, 和 `PRIVATE` 关键字用于指定目标的链接库和编译选项的可见性。这些关键字通常与 `target_link_libraries` 和 `target_compile_options` 等命令一起使用。  


- `PRIVATE`：如果你将一个库或选项标记为 `PRIVATE`，那么它只会影响到当前目标。它不会传递给链接到当前目标的其他目标。  
  
- `INTERFACE`：如果你将一个库或选项标记为 `INTERFACE`，那么它不会影响到当前目标，但会传递给链接到当前目标的其他目标。  
  
- `PUBLIC`：如果你将一个库或选项标记为 `PUBLIC`，那么它既会影响到当前目标，也会传递给链接到当前目标的其他目标。  
  
  例如，假设你有两个目标 `A` 和 `B`，并且 `A` 链接到 `B`。如果你将一个库 `L` 作为 `PRIVATE` 链接到 `A`，那么只有 `A` 可以使用 `L`。如果你将 `L` 作为 `INTERFACE` 链接到 `A`，那么只有 `B` 可以使用 `L`。如果你将 `L` 作为 `PUBLIC` 链接到 `A`，那么 `A` 和 `B` 都可以使用 `L`。

## Conan

### conan self.copy

`conan self.copy()` 是 Conan 包管理器中的一个函数，用于在构建脚本中复制文件到指定目录。

具体而言，`self.copy()` 函数用于将构建过程中生成的文件从构建目录复制到指定的目标目录。它通常在 `build()` 方法中使用，用于自定义构建逻辑。

`self.copy()` 函数的语法如下：

```python
self.copy(pattern, dst, src=None, root_package=None, keep_path=False, links=False)
```

参数说明如下：

- `pattern`: 文件名模式，支持通配符和正则表达式来匹配文件。

- `dst`: 目标目录，表示文件复制到的目标位置。

- `src`: 源目录，表示文件的原始位置。默认情况下，文件将从构建目录中复制，可以通过指定 `src` 参数来自定义源目录。

- `root_package`: 根包名，用于指定根包的名称。默认情况下，如果构建是由根包发起的，不需要指定此参数。但如果构建是由子包发起的，需要指定根包的名称。

- `keep_path`: 是否保持文件的相对路径结构。默认为 `False`，表示复制文件时将忽略其相对路径，仅保留文件名。

- `links`: 是否复制文件的符号链接。默认为 `False`，表示复制实际文件而不复制符号链接。

使用 `self.copy()` 函数可以根据需要在构建过程中复制所需的文件到指定的目录，以满足构建和部署的要求。具体的使用方法和参数配置可能会因具体的构建脚本和项目而有所不同，建议查阅相关文档和示例来获取更详细的信息。
